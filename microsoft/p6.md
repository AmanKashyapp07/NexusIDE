## 3. Visual Deep-Dives: The 3 Canonical Systems Postmortems

### Postmortem 1: Node.js 8KB Shared Buffer Pool Slicing Corruption

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                    POSTMORTEM 1: V8 8KB ARRAYBUFFER POOL SLICE CORRUPTION                        │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘

 [ V8 8KB Shared Memory Slab ]
 ┌──────────────────────┬──────────────────────────────────────────┬───────────────────────────────┐
 │ Unrelated Memory     │ Sliced Yjs Delta (42 Bytes)              │ Unrelated Memory              │
 │ (Bytes 0 to 2047)    │ byteOffset: 2048  |  byteLength: 42      │ (Bytes 2090 to 8191)          │
 └──────────────────────┴──────────────────────────────────────────┴───────────────────────────────┘
                                ▲
                                │
   AI'S NAIVE INSTANTIATION:    │   CORRECT CANDIDATE FIX:
   new Uint8Array(buf.buffer)   │   new Uint8Array(buf.buffer, buf.byteOffset, buf.byteLength)
   ──────────────────────────   │   ──────────────────────────────────────────────────────────
   • Ignores buf.byteOffset!    │   • Explicitly starts at byte 2048!
   • Reads from Byte 0!         │   • Reads exactly 42 bytes!
   • Binary decoder gets junk   │   • CRDT state vector converges perfectly!
     bytes from unrelated HTTP! │
```

| Dimension | Details |
| :--- | :--- |
| **Symptom** | Intermittent `Unexpected end of array buffer` decoding crashes on Pod 2 under heavy concurrency. |
| **Root Cause** | Node.js slices buffers $<4\text{KB}$ from an internal 8KB slab (`Buffer.poolSize = 8192`). `buf.buffer` returns the entire slab. Omitting `byteOffset` reads unrelated memory starting at byte 0. |
| **The Fix** | Enforced `new Uint8Array(buf.buffer, buf.byteOffset, buf.byteLength)` across all binary decoders in `redisAdapter.service.ts`. |
| **Prevention** | Created `testing/services/buffer_offset.test.ts` to fuzz-test buffer decoders with pre-dirtied 8KB memory slabs. |

### Postmortem 2: Redis Pub/Sub Infinite Message Rebroadcast Storm

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                    POSTMORTEM 2: RECURSIVE REDIS PUB/SUB BROADCAST STORM                         │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘

 [ INFINITE FEEDBACK STORM ]
  Pod 1 ──► PUBLISH update ──► Redis ──► Pod 2 receives ──► Calls Y.applyUpdate()
    ▲                                                            │
    │                                                            ▼
    │                                              Fires local 'update' event!
    │                                                            │
    └────────── Redis ◄── Pod 2 RE-PUBLISHES update back! ◄──────┘
    [ CASCADE: Both pods peg at 100% CPU; millions of commands/sec; server crashes in 3 seconds ]

 [ CANDIDATE FIX: ORIGIN-TAGGED LOOP GUARD ]
  Pod 2 receives from Redis ──► Y.applyUpdate(doc, update, 'redis')
                                       │
                                       ▼
                               doc.on('update', (data, origin) => {
                                 if (origin !== 'redis') { // DETERMINISTIC LOOP BREAKER!
                                   publishToRedis(data);
                                 }
                               });
```

| Dimension | Details |
| :--- | :--- |
| **Symptom** | Typing 1 character caused immediate 100% CPU spike on all backend pods; Redis flooded with millions of messages/sec. |
| **Root Cause** | Applying updates received from Redis triggered local Yjs `update` listeners, which published the same update back to Redis. |
| **The Fix** | Tagged incoming Redis updates with `origin: 'redis'`; gated outbound publication on `if (origin !== 'redis')`. |
| **Prevention** | Created `chaos_redis.test.ts` verifying that injecting an update results in exactly 1 message published to Redis. |

### Postmortem 3: Monaco Double-Binding Tab-Switch Memory Leak

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                    POSTMORTEM 3: MONACO TAB-SWITCHING DOUBLE-BINDING LEAK                        │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘

 Tab Switch: File A ──► File B
 ┌────────────────────────────────────────────────────────────────────────────────────────────────┐
 │ The Bug: MonacoBinding A was NEVER destroyed!                                                  │
 │ • Interval tree inside Monaco retains stale ranges: +15MB RAM per tab switch                   │
 │ • Remote collaborator cursors duplicate; ghost cursors frozen on screen                        │
 └───────────────────────────────┬────────────────────────────────────────────────────────────────┘
                                 │
                                 ▼
 ┌────────────────────────────────────────────────────────────────────────────────────────────────┐
 │ The Fix: Deterministic React Cleanup Lifecycle (useCodeEditorSetup.ts)                         │
 │ 1. awareness.off('change', handleAwarenessChange)                                              │
 │ 2. editor.deltaDecorations(localDecorations, []) ◄── Explicitly purges DOM glyphs from engine!  │
 │ 3. binding.destroy() ◄── Dismantles y-monaco listeners cleanly!                               │
 └────────────────────────────────────────────────────────────────────────────────────────────────┘
```

| Dimension | Details |
| :--- | :--- |
| **Symptom** | Remote cursors duplicated on screen; tab switching caused browser memory to climb by 15MB per switch (450MB+). |
| **Root Cause** | Switching tabs re-ran `useEffect` without destroying previous `MonacoBinding` or clearing native decoration IDs. |
| **The Fix** | Added deterministic cleanup: invoked `binding.destroy()` and `editor.deltaDecorations(ids, [])` on unmount. |
| **Prevention** | Created Playwright memory leak test (`tab_memory_leak.test.ts`) asserting $< 5\text{ MB}$ heap growth after 100 tab switches. |
