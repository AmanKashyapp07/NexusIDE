# Phase 3 — Sandboxing, Container Lifecycle & PTY Streaming

**Subsystems Covered:** Pre-Warmed Docker Container Pool (`pool.ts`) + Workspace Container Allocator & cgroups v2 Freezer (`workspaceContainer.ts`) + Container Lifecycle Service (`containerLifecycle.service.ts`) + Docker PTY Terminal Exec Handler (`terminalHandler.ts`) + Language Server Protocol Bridge (`lspHandler.ts`)  
**Target Role:** Microsoft Software Engineering Internship Interview  
**Core Purpose of this Document:** Visual technical breakdown of how NexusIDE isolates untrusted code execution inside hardened Linux containers, delivers <50ms container cold-starts via pre-warmed pooling, multiplexes independent Unix pseudo-terminals (`/dev/pts/X`) within a shared container, and freezes idle workspaces via Linux kernel cgroups v2.

### Comparative Architecture Table: Sandboxing Paradigms

| Feature / Metric | 1 Container / Workspace (NexusIDE) | 1 Container / User | MicroVMs (Kata / Firecracker) | Bare Host Execution |
| :--- | :--- | :--- | :--- | :--- |
| **Cold Start Latency** | **$< 50\text{ ms}$** (Warm Pool) | 3.2s–4.5s per user | 80ms–150ms | Instant (0ms) |
| **Host RAM Overhead** | **Lowest** (850MB for 5 users) | Extreme (5GB+ for 5 users) | Low (5MB base per microVM) | None |
| **Filesystem View** | **Unified** (shared builds / npm) | Fragmented / Divergent | Isolated | Shared (No Isolation) |
| **Terminal Isolation** | **Complete** (`/dev/pts/X` PTYs) | Complete | Complete | Zero |
| **Kernel Security** | Shared Host Linux Kernel | Shared Host Linux Kernel | **Dedicated Guest Kernel** | None (Fatal) |
| **Fork Bomb Defense** | **cgroups `pids.max = 500`** | cgroups `pids.max` | Hypervisor PID cap | Host OS Freezes |

## 3. Linux Kernel cgroups v2 Resource Enforcement & Security Limits

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                  LINUX CGROUPS V2 KERNEL HIERARCHY & FORK BOMB DEFENSE                           │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘

 Host Linux Kernel cgroups v2 Root: /sys/fs/cgroup/docker/<container_id>/
 ├── pids.max = 500              ◄── HARD CEILING: Maximum 500 processes allowed
 ├── memory.max = 1073741824     ◄── HARD CEILING: 1GB RAM (OOM Killer triggers SIGKILL exit 137)
 ├── memory.swap.max = 0         ◄── SWAP DISABLED: Prevents disk thrashing on host
 └── cpu.max = 150000 100000     ◄── CPU LIMIT: Max 1.5 cores per 100ms CFS scheduling period

────────────────────────────────────────────────────────────────────────────────────────────────────

 [ KERNEL FORK BOMB EXECUTION TRACE: :(){ :|:& };: ]
 
   Attacker Shell                    Linux Kernel (pids cgroup)               Host OS VM
 ┌────────────────────────┐         ┌────────────────────────┐              ┌────────────────┐
 │ Runs :(){ :|:& };:     ├────────►│ fork() / clone() syscal│              │ Healthy        │
 │ Spawns process 2, 4, 8 │         │ Increments pids.current│              │ Event Loop Lag │

                                                │

                                    Returns errno: EAGAIN
```

## 4. Visual Failure Modes & Recovery Mechanics

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                         5 CRUCIAL FAILURE MODES: SYSTEM BEHAVIOR MATRIX                          │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

| Failure Mode | Root Trigger | Immediate System Impact | Recovery / Mitigation Mechanism | Automated Verification |
| :--- | :--- | :--- | :--- | :--- |
| **1. Malicious Fork Bomb** | User runs `:(){ :|:& };:` in terminal. | Container rapidly spawns processes toward infinity. | Kernel `pids.max = 500` enforces hard limit; kernel returns `EAGAIN`. Host OS remains 100% responsive. | `test.sh --security` |
| **2. Container OOM Exhaustion** | Memory leak script exceeds 1GB RAM. | Container memory touches `1073741824` bytes. | Kernel OOM killer sends `SIGKILL` (exit 137) to child process. Host and Node.js gateway unharmed. | `test.sh --security` |
| **3. Terminal Process Exit** | User types `exit` or runs `kill -9 $$`. | Underlying PTY `/dev/pts/X` stream terminates. | Dockerode emits `end`; UI shows "Restart Terminal" button. Re-spawns PTY via `container.exec()` without rebooting container. | `test.sh --pty-stress` |
| **4. Docker Daemon Hang** | 30 concurrent launches overwhelm Docker socket. | Docker API socket `/var/run/docker.sock` stops responding. | All calls wrapped in 10-second `Promise.race()` timeout watchdog, preventing unhandled event loop promise hangs. | `test.sh --chaos` |
| **5. Zombie Containers** | User closes laptop lid without logging out. | Idle container continues consuming 250MB+ RAM. | Automated background reaper runs every 5 minutes; force-purges containers idle $> 30\text{ mins}$. | `test.sh --integration` |

## 6. Microsoft-Specific Technical Anchors

### Connection to GitHub Codespaces & Dev Containers
- **Codespaces Architecture:** Mirrors NexusIDE's container design: bridges browser xterm.js via WebSockets to an in-container agent, mounting `/dev/pts/X` pseudo-terminals.
- **Prebuilds:** Codespaces pre-builds containers; NexusIDE's `WarmPoolManager` pre-boots them in RAM to deliver $< 50\text{ ms}$ launch latency.

### Hyper-V & Kata Containers in Azure
- In Azure Container Apps and Azure Cloud Shell, untrusted tenant workloads run inside **Azure Kata Containers** (utilizing light Hyper-V hypervisor isolation) to guarantee hardware virtualization boundaries between tenants.
